# P4.1 工作流性能测试

该测试使用确定性合成监测序列，在一次性 PostgreSQL 17、独立 Platform/Data/Execution 数据库、真实 HTTP 服务、Worker、Toil 9.5.0 和受信算子容器上运行。它不读取部署数据库，也不使用 V6 资源。合成数据不是实际地下水观测。

## 长节点方法

主性能场景不使用短计算节点。测试专用算子镜像为每个计算节点执行固定 **30 CPU 秒**的确定性负载，然后调用正式完整率或线性趋势算子。请求不能改变负载时长。节点仍受生产执行器的普通用户、只读根目录、禁网、1 CPU、1 GiB 内存和稳定身份约束，并继续经过授权、预算、Toil、输出核实、原子发布和独立验收。

该镜像只存在于 `tests/performance`，不登记到生产算子目录，也不增加生产接口或运行时开关。基准读取其不可变镜像 ID；任一计算容器实际运行不足 25 秒会直接失败。

## 运行

```bash
bash scripts/checks/check_p4_performance.sh --profile quick
bash scripts/checks/check_p4_performance.sh --profile standard
```

统一入口会清除继承的 `V7_*` 环境变量、同步锁定依赖、重建生产镜像及测试专用长节点镜像、运行生成器和工作流契约测试，再启动一次性服务执行基准。结果写入 `${V7_P4_RUNTIME_ROOT}/verification/p4-workflow-performance-evidence.json`。进程、容器、数据库角色、数据库和临时文件在结束时回收。

`quick` 用于修改后的快速检查；`standard` 是本阶段的固定单机性能基线；`max` 用于人工压力探索，不属于常规验收。

| 配置 | 数据边界闭环 | 全计算 scatter |
| --- | --- | --- |
| quick | 2 万行、200 组、2 个并行长节点 | 2 万行、200 组、4 个长节点、任务并发上限 2 |
| standard | 10 万行、1000 组、2 个并行长节点 | 5 万行、500 组、8 个长节点、任务并发上限 4 |
| max | 10 万行、1000 组、2 个并行长节点 | 10 万行、1000 组、16 个长节点、任务并发上限 8 |

## 场景和判定

1. **数据边界闭环**达到当前 CSV 行数和分组数上限，同时运行完整率与线性趋势。两个节点都执行固定长负载和正式科学计算，原子发布命名成果，再由独立 Decimal 检查器验收并完成任务。预算必须精确结算为两次算子执行和一次检查。
2. **全计算 scatter**把全部组确定性分为不重叠批次，执行 dotproduct scatter。所有实例都启用并运行固定长负载。节点必须有唯一身份，预算和发布资产数必须等于节点数，观测到的在途数不得超过任务并发上限。

基准记录数据生成、上传与导入、包验证、首节点、工作流、独立验收、每个算子容器、预算和输入扫描数据，同时检查节点容器的隔离和资源限制。短分支展开不再作为主性能结果。

这些数字用于同一机器和相同镜像上的回归比较。单次观测会受到冷缓存、Docker、PostgreSQL 和主机负载影响，不能直接作为生产容量、SLA 或跨主机扩展结论。报告必须同时解释节点计算时间、有效并行度和 Toil/CWL 服务协调时间。
