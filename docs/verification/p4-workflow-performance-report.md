# P4.1 长节点工作流性能报告

> **HISTORICAL.** 本报告是该阶段的冻结实现或验收记录，不代表当前活动 Release 或当前实现状态。当前发行身份见 [当前发布指针](p82-current-release.json)。

日期：2026-10-12。版本：V7 `0.3.0`。本轮是 P4.1 的补充性能验收，不进入 P4.2，不修改生产状态机、接口或数据库迁移。

**结论：长节点功能闭环通过，并行效率仍需优化。** `bash scripts/check_p4_performance.sh --profile standard` 退出码为 0。10 个计算节点全部实际运行 30.52–31.24 秒，没有短节点；预算、节点身份、原子发布和独立验收均正确。8 节点 scatter 的计算窗口有效并行度为 1.41/2，使用了约 70.6% 的两核并行能力；把启动、收集和发布计入后，端到端有效并行度为 1.07。

[结构化证据](p4-workflow-performance-evidence.json) 是本次标准规模运行结果。所有输入都是仓库内生成规则产生的确定性合成数据，不是真实地下水观测。

## 测试方法

测试专用镜像在每个节点内先消耗固定 30 CPU 秒，再调用交付版本中的正式科学算子。负载时长不接受 API、工作流输入或环境变量控制。Execution 仍以不可变镜像 ID 创建容器，使用普通用户、只读根目录、禁网、1 CPU 和 1 GiB 内存。测试继续走公开上传、任务、精确授权、父额度、Toil 节点身份、发布和验收接口。

基准设有独立门槛：每个计算容器必须至少运行 25 秒。测试专用镜像未加入生产目录，不改变生产算子行为。原先使用大量跳过分支和单个亚秒节点的结果已经从性能基线移除，因为它测量的是短作业调度，不代表科学计算工作流性能。

生成器固定规则为：组按 `G0000` 起编号，记录按组轮转，时间从 `2024-01-01T00:00:00Z` 起按每组样本序号逐小时增加，值为 `100 + group/100 + sample/8`。标准边界文件为 4,300,019 字节，SHA-256 为 `f70513d0623332fc8a7feb6141c7a5c8d56c6f13d7647dcaeb14ffa86cef05ae`。

## 问题分析

长节点本身稳定。10 个节点时长差异小于 0.8 秒，两个场景都只使用一个 Toil 引擎代次，失败 Worker 为 0，也没有发生节点换身份或重复扣费。这说明节点运行和账本恢复规则没有成为本次失败源。

瓶颈在调度并行度。Toil 当前固定 `--maxCores 2`，因此任务并发上限 4 本来就最多只能得到 2 个并行节点。双算子场景的两个容器只相隔 0.224 秒启动，有效并行度达到 1.979，证明 Execution 和许可链路能够同时运行两个节点。scatter 的启动偏移为 0、11.13、39.41、57.88、85.68、100.05、134.95 和 142.53 秒，批次之间存在约 7–35 秒没有用满两核的空档。其计算窗口有效并行度为 1.412，端到端为 1.070。问题更接近 Toil/CWL 的 scatter 子流程作业图、包装器调度和节点交接空档，而不是 Execution 完全串行。单纯提高 Platform 的任务并发上限不会解决它。

Toil 日志还记录了边界场景 2 次、scatter 场景 17 次进程组回收警告。它们没有导致失败或换代引擎，但与每个 CWL 包装器作为独立短调度作业运行有关，应在扩大节点数前单独处理。下一步应测量包装器、许可往返、输出交接和 Toil 作业之间的空档，再决定是否调整 chaining、作业资源声明或桥接批处理。任何优化都必须保留稳定调用路径、节点许可、旧引擎隔离和未知状态不重算。

- `quick` 预运行：2 万行双算子和 4 节点全计算 scatter 通过，6 个节点均约 30.5 秒。

本轮是单次、单主机观测；宿主机不是隔离的性能实验机。没有测量重复运行分布、持续多租户负载、跨主机、磁盘故障、备份恢复或生产 SLA。`max` 档未作为本轮通过条件执行。P4.1 的 365 项功能回归未因测试专用镜像变更而重跑；统一性能入口真实复用了相同 API、数据库、Worker、Toil、发布和检查器路径。
