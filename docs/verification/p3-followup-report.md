## 本轮发现与修复

| 问题 | 处理和对应回归 |
| --- | --- |
| 原始 Parquet 虽有 f0/f1 清单但物理列仍是原名，可能在算子运行时 KeyError | Data 只允许已核实的 `normalized` Parquet 进入输入绑定；原始表示返回 `409 INVALID_BINDING`，规范化表示仍可执行。 |
| 已持久接受的执行命令重放先访问 Data，Data 停机时错误返回 503 | 在外呼前查询本地已提交的幂等记录，核对冻结 Action 的原始请求；同键同内容返回原命令，同键改内容 409。重放仍重新检查当前令牌及项目角色，撤销/降权分别返回 401/403。 |
| 检查器只比较方法文件和成果文本是否相同，未检查方法声明本身 | 独立检查器固定两个算子的允许方法声明；伪造“显著因果预测”等声明即使与方法文件一致也 FAIL。候选成果数量不一致产生 `OUTPUT_COVERAGE` FAIL，不再抛出检查器异常。 |
| Execution 遇到 HTTP 5xx 时以 0.2 秒无界快速轮询 | 与通信故障统一使用 1、2、4…秒、上限 30 秒的恢复间隔；保持未知占用，不把 5xx 当明确拒绝。 |
| Data 导入和 Execution 长步骤可能超过 30 秒租约后被另一个 Worker 接管 | 两服务按数据库时钟续租，代次和有效期仍约束每次权威回写；超过原租约时长的并发测试证明第二个 Worker 无法领取。 |
| P3 公共查询缺少具体 OpenAPI 响应模型；页面在重复计算后把所有成果登记为一个超过 2 项上限的候选 | 上传、资产、算子、执行、候选和验收响应增加 DTO；页面分别选择一项已发布完整率及趋势成果，三项计算加一次验收的浏览器闭环通过。 |

新增用例均先复现原行为或缺口，再修复并定向运行。统一检查首次因新增 SQLAlchemy 异常导入违反 Execution 应用层边界而失败；移除该依赖后重新运行。缺项检查器用例补入后再次完整运行，只有最后一次成功运行用于本报告。
