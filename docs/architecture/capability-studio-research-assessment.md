# 算子与工作流工作台：开源调研与二次设计评估

日期：2026-10-16。评估对象为实施计划 1.1；当前[实施计划](capability-studio-implementation-plan.md)已在吸收评估后完成 1.3 审计。源码基线：P7.3a / `0.13.0`。

后续处理：用户要求优化后，本报告 E-01–E-07 已合入 v1.2，映射见计划 13.1。下文保留评估时的证据与建议语境；“已合入设计”不表示软件已经实施。

结论：**总体架构有条件通过。保留独立前端、Platform 应用模块和既有执行链路；补齐编辑语义与测试证据，评估简化首轮部署改造。**

本报告包含官方资料调研、源码核对和三个实际运行的只读契约探针。它不是软件验收报告，不证明拟新增模块已经实现。原计划中已解决的 19 项反馈仍见[首次评估记录](capability-studio-design-review.md)，不重复算作新发现。

## 1. 评估方法与证据范围

本轮核对：

- 当前算子目录、参数 DTO、自定义校验、Data 精确输入解析。
- 工作流编译器支持范围、Action 准入与幂等恢复路径。
- release lock 构建及加载代码。
- 计划中的 A1–A5、AuthoringDescriptor、字段预览、候选、试运行、版本发布与发行身份。
- QGIS、Galaxy、Planemo、Dockstore、JSON Forms、React Flow 和 CWL 官方文档。

本轮没有运行 PostgreSQL、Docker、Toil、浏览器或完整兼容回归；没有改动业务代码、数据库、部署和 V6。

证据用语区分：

- **已复现**：本轮实际执行探针得到的行为。
- **源码事实**：读取当前代码确认的接口和约束。
- **设计缺口**：拟建模块的协议还不足以指导实现，不等于现有系统存在故障。
- **建议**：结合资料与当前工程作出的取舍，尚未采用或实现。

## 2. 成熟项目真正值得借鉴的部分

| 项目 | 官方资料确认的能力 | V7 应采用的部分 | 不应直接推导出的结论 |
| --- | --- | --- | --- |
| QGIS Model Designer | 模型输入、算法输入/输出连线、单独的 Dependencies 参数 | 参数来源清晰；数据依赖与执行顺序分别表达 | 画一条线就能在 V7 中实现任意控制依赖 |
| Galaxy | 工作流重构有连接、断开、工具升级和 dry_run 等明确操作 | 更换算子版本时先展示参数、连接和输出变化，创建新修订 | 可以静默升级旧流程或自动删除不兼容连接 |
| Planemo | 工作流测试包含输入和输出断言，并生成机器可读报告 | 把“运行成功”和“满足样例预期”分开记录 | 进程退出成功就等于工作流经过充分验证 |
| Dockstore | 快照冻结描述文件、测试参数和版本元数据 | 不可变候选与精确版本复用 | 快照已经通过真实执行或科学验收 |
| JSON Forms | JSON Schema/UI Schema 驱动表单，可接入后端错误 | 作为表单候选组件；服务端规则仍为权威 | 导出 JSON Schema 就包含所有 Pydantic 跨字段规则 |
| React Flow | 自定义节点和连接交互 | 负责画布、选择、连线和布局 | 负责 V7 的 CWL、授权、预算或科学语义 |

对应来源：[QGIS Model Designer](https://docs.qgis.org/3.44/en/docs/user_manual/processing/modeler.html)、[Galaxy refactor API](https://docs.galaxyproject.org/en/release_26.1/lib/galaxy.workflow.refactor.html)、[Planemo 测试格式](https://planemo.readthedocs.io/en/stable/test_format.html)、[Dockstore 快照](https://docs.dockstore.org/en/stable/advanced-topics/snapshot-and-doi.html)、[JSON Forms 后端错误接入](https://jsonforms.io/docs/validation/)、[React Flow 自定义节点](https://reactflow.dev/learn/customization/custom-nodes)。Galaxy 引用的是其版本化开发文档中的设计事实，不构成推荐部署该开发版本。

没有证据支持为了这个模块替换 Toil、引入第二套注册服务或迁入整个 Galaxy。当前最合适的组合仍是：成熟前端组件 + V7 自身受限契约 + 原有运行内核。这是本项目的工程判断，不是这些项目共同规定的架构。

## 3. 当前计划应保留的设计

1. **后端留在 Platform。** 草稿与候选关联可以使用现有事务；试运行不会额外增加一个跨服务调度事务。
2. **CWL 源对象唯一权威。** 图形是投影，layout 单独保存，避免两个可独立修改的执行定义。
3. **候选复用现有 PackageRef。** 发布只增加系列版本与证据映射，不另造可执行包格式。
4. **Trial 与 Action、预算、Command、outbox 原子创建。** 新界面不会因为响应丢失产生第二次计算。
5. **登记、部署与运行区分。** 项目 OWNER 不因此获得全局镜像部署权；提交登记材料不会改变 Operator Catalog。
6. **试运行、版本发布与科学验收区分。** 同一成功试运行可以证明样例运行事实，但不能授予 VERIFIED Completion。
7. **每轮只完成当前范围。** A1、A2 没有运行接口，A3 才交付完整编辑闭环；高级 CWL 先只读保护。

这些边界已经覆盖主要一致性风险，下一步应让它们更容易实现和使用，而不是再增加一套抽象平台。

## 4. 必须补齐的编辑与测试语义

### E-01：JSON Schema 表单必须落实到现有跨字段规则

**性质：已复现的表达能力差异；A1 契约门槛、A2 表单门槛。**

对当前 [science.py](../../packages/contracts/src/platform_contracts/science.py) 执行 `model_json_schema()`，分别使用 JSON Schema Draft 2020-12 和原 Pydantic DTO 校验：

| 输入 | 导出 Schema | 原 DTO |
| --- | --- | --- |
| `ROW_COUNT` 未提供任何行数边界 | 接受 | 拒绝 |
| `COUNT_ROWS` 同时提供 `field_id` | 接受 | 拒绝 |
| Profile 的 `fields=["f0","f0"]` | 接受 | 拒绝 |

**这不是现有 API 放过非法请求。** 现有 DTO 正确拒绝；它证明仅依赖生成 Schema 的编辑器会给出错误的“参数有效”提示。

计划 6.1 已承认这个限制，首次评估 R-08 也已指出。本轮增加的是复现证据和实现门槛：

- 为当前 11 个算子列出表单类型、条件字段、空值/省略/默认值语义、服务端专有校验和错误定位。
- 不适用字段不能因控件隐藏而被静默带入请求；也不能为通过校验擅自删除已有用户值。
- 选择 JSON Forms 或自建少量控件前，先验证 Rule record、Aggregate measures 和 Filter 联合三类复杂表单。
- 服务端错误映射到 `step_key + JSON pointer`；前端通过只能显示“基础检查通过”，不能替代后端验证。
- 明确禁止未经用户操作的类型强制转换、默认值写回、未知字段删除和数值舍入。

JSON Forms 的 `additionalErrors` 能显示后端字段错误，适合作为候选，但仍需要受信控件和契约回归。[官方说明](https://jsonforms.io/docs/validation/)

**新增验收：** 上述三组输入在页面上不能显示最终有效；错误能定位；修正后往返保存参数不变。测试同时覆盖省略、null、默认值和规范数字字符串。

### E-02：必须明确连线表示数据传递，不能冒充控制依赖

**性质：源码支持范围与产品语义缺口；A2 必须写清。**

当前 [workflow_compiler.py](../../packages/platform-core/src/platform_core/application/workflow_compiler.py) 的 step 白名单只包含 `run/in/out/scatter/scatterMethod/when/label/doc`，没有独立的 `dependsOn`；输入绑定也必须对应算子真实输入端口。

因此以下两种意图不同：

```text
Filter 输出表 → Aggregate 输入表           当前支持的数据流
Validate 成功 → 才允许 Aggregate 读取原表    独立控制依赖，当前没有通用契约
```

`table-validate.table` 是每条规则一行的结果表。把它连给 Aggregate，会统计规则报告，不会自动传递原始输入。把两者都连接原表，只形成并行分支；父级原子发布可以阻止半组成果公开，却不能保证 Aggregate 在校验之前完全不计算、不计费。

QGIS 为这种情况提供单独的 Dependencies；CWL 的基本执行依赖来自数据链接，无依赖的步骤可以并发。这说明两类语义需要明确区分，并不意味着应立刻向 V7 增加控制边。[QGIS](https://docs.qgis.org/3.44/en/docs/user_manual/processing/modeler.html)、[CWL 执行模型](https://www.commonwl.org/v1.2/Workflow.html)

建议首期只提供数据流连线，帮助信息明确 Validate 的输出用途。不通过隐藏伪输入、虚假 File 或前端画面顺序模拟控制依赖。后续确有校验门控需求时，再单独设计受信门控契约及预算/失败规则。

**新增验收：** 节点左右位置不能改变执行依赖；Validate 与 Aggregate 并联时页面说明并发语义；不存在“校验通过后才计费”的错误承诺。

### E-03：字段结构预览需要一个真实、只读的绑定入口

**性质：计划已有目标，但接口链路不完整；A2 需要补齐。**

计划 6.3 定义了结构转换和 `REQUIRES_BINDING`，8.2 的接口列表却没有说明编辑时如何把真实输入结构送给这些规则。只有描述符无法知道用户的 `f0` 是字符串还是数值、Project 后还剩哪些字段。

当前 [Data.resolve](../../apps/data-service/src/platform_data/application/data.py) 已核对项目、精确 AssetRef、表示摘要及受信字段描述，可以复用，不需要新资产服务。

建议增加一个**只读、有界的结构预览用例**，经 Platform 鉴权后调用 Data：

```text
精确草稿修订 + 根端口的样例 AssetRef/Selection
→ 当前访问权和精确摘要检查
→ Data 技术结构
→ 按拓扑传播受信结构规则
→ 每个端口的字段/类型/CRS、未知项及错误位置
```

关键限制：

- 预览绑定与可复用模板源定义分开；选择样例不悄悄把资产硬编码到模板。
- 预览不创建 Action、预算、包或新的长期状态机，不运行科学容器。
- 仅返回结构，不返回原始行、频数或样本值。
- 未保存编辑可使用明确的临时 source digest；响应必须回显摘要，前端丢弃过期结果。
- 修改上游 Project/Cast/Aggregate 时，其下游结构提示失效；不能沿用旧字段列表。
- 未知输入保持 `REQUIRES_BINDING`；预览成功不授予 grant，试运行仍重新核对输入。
- POST 若用于只读计算，不创建持久资源；若未来保存预览证据，应另外定义写入与幂等语义。

**新增验收：** 结构请求乱序返回、切换项目、删除字段、改变字段类型、替换资产摘要、跨项目引用、未绑定输入均有确定行为。

### E-04：试运行证据必须冻结“期望验证什么”

**性质：计划文字已有断言摘要，但 DTO 与发布条件尚未落实；A3 门槛。**

“父执行成功且成果已发布”是运行事实，不足以证明一个具体版本完成了预期行为。例如，空 scatter 不执行任何实例；条件为 false 可以跳过关键算子。这些是合法 CWL 行为。[CWL scatter 定义](https://www.commonwl.org/v1.2/Workflow.html)

Planemo 的测试模型同时描述输入和输出断言；Dockstore 的快照定义只负责冻结材料，不能把“已登记快照”直接解释成“测试通过”。[Planemo](https://planemo.readthedocs.io/en/stable/test_format.html)、[Dockstore](https://docs.dockstore.org/en/stable/advanced-topics/snapshot-and-doi.html)

建议在既有 Trial 请求/记录内冻结一个有界 `trial_case`，不另建测试服务：

- candidate、输入摘要和预期结果摘要。
- 必须实际执行的稳定步骤路径；高级 scatter 到 A5 再补实例/分支覆盖。
- 必需最终输出端口、允许的空值及集合形状。
- 使用固定白名单检查 Schema、摘要或测试夹具约定，不开放用户表达式和脚本。
- 分别保存 `execution_outcome` 与 `case_verdict`；断言失败不能改写已经成功的 Execution。
- 测试材料必须在提交前冻结，不能看到结果后补填“期望”。

Studio 发布仍要求至少一条正向真实成功用例；失败/拒绝用例可作为额外证据，不能单独替代正向用例。页面显示“在这些样例上通过”，不显示“所有输入正确”或“科学已验证”。Assertions 只核验已发布事实，不赋予读取节点私有文件的权限。

**新增验收：** 空 scatter、跳过关键节点、错误输出形状不能获得该样例的通过标识；断言修改后不能复用旧 trial_case 摘要；断言失败不会删除已发布事实。

## 5. 可以减少维护成本的调整

### E-05：A1 不必先把描述符做成新的全平台部署附件

**性质：可选简化建议，不是现有 release lock 缺陷。**

评估时的计划 1.1 第 12.2 节将描述符作为外部部署产物，因此需要扩展 release lock 并更新各消费端。这个设计可以成立，但使 A1 同时承担前端、草稿和全平台发行格式升级。

存在更轻的候选方案：

```text
已锁定 wheel 内的参数 DTO + 受信结构/UI 映射
                         + 已校验 Operator Catalog
                         ↓
              Platform 确定性派生编辑描述
                         ↓
        描述摘要、输入身份及前端握手信息
```

适用前提：

1. 描述符没有来自工作区、数据库、用户或可替换文件的额外语义。
2. 生成逻辑及映射随 wheel 交付；静态前端也已打入 API wheel。
3. 安装流程确实校验 wheel 文件摘要；不能以版本字符串相同代替产物完整性。
4. 生成结果确定，缓存按输入摘要隔离；每次校验记录精确描述身份。
5. 继续保留 Platform/Execution/Agent 的既有运行目录与 release lock 校验。

这样无需仅为 UI 派生视图立即升级 release lock 格式。若描述符要脱离服务发行、供外部维护或独立替换，则应保留原计划中的外部文件锁定方案。

源码依据：[发行锁构建](../../scripts/build_p7_release_lock.py)、[release.py](../../packages/contracts/src/platform_contracts/release.py)。当前加载器校验 schema_version、摘要及相应目录/镜像；不应把它描述为所有顶层键都使用严格 DTO 校验。是否调整格式应取决于是否新增独立权威产物。

**建议 A1 第一项先用真实构建产物验证上述前提，再固定一种方案。不得同时维护外部描述符与运行时派生描述符两种生产权威。**

### E-06：显示信息与语义校验身份分开

**性质：避免不必要重验的设计建议；不放松运行锁。**

当前描述符同时包含约束和 UI hints；若统一摘要直接作为校验有效性的唯一依据，改一段帮助文字可能让全部草稿显示过期。

建议把身份至少分为：

- `semantic_contract_digest`：端口、参数约束、结构规则、受信校验器版本。
- `presentation_digest`：标签、说明、分组和纯展示布局。

完整发行身份继续记录。纯显示变化不应被解释为参数或数据绑定失效；语义变化必须重新验证。当前 Operator Catalog 的精确冻结和执行准入规则保持不变，不能在本轮顺便放宽为“看起来兼容”。

只按所用算子依赖集合失效、跨发行复用测试等更复杂优化暂缓。没有数据证明需要时，不增加自动迁移或兼容判定引擎。

### E-07：登记中心要清楚说明它管理接入材料

**性质：已在计划中正确约束，需要贯彻到页面和交付口径。**

当前执行仍存在 OperatorId、参数联合、受信实现和输出校验白名单。因此这个模块能帮助审核和追踪接入，但不能让用户提交 JSON 后立刻新增算法。

保留 A4；优先让 A1–A3 产生真实编辑价值。A4 复用现有发行 CLI，不增加自动代码获取、构建集群、在线安装或另一套审批平台。项目审核与平台维护权限继续分离。

以后若要“无需改平台代码接入新算子”，必须另立扩展协议课题，覆盖通用参数、输入输出、执行适配、独立检查器与 Agent 约束。不能把这个目标藏在本次工作台实施中。

## 6. 建议调整后的逐轮门槛

保留 A1–A5，不增加新的正式轮次，也不将 A3 运行功能提前塞入 A1。

| 轮次 | 原目标保留 | 本次需补齐或简化 | 结束时可以宣称 |
| --- | --- | --- | --- |
| A1 | 描述符、草稿、修订、权限、最小页面 | 先证明 11 个算子的契约覆盖；锁定描述符交付方案；复现跨字段差异 | 可保存和精确读取草稿，目录说明可靠 |
| A2 | 基础画布、参数表单、受信校验 | 只读结构预览；数据流语义；后端错误定位；省略/null/默认值往返 | 可以正确编辑当前支持的基础流程 |
| A3 | 候选、真实试运行、版本发布 | 冻结 trial_case；分别记录运行事实和样例判定；复用原预算与发布 | 用户可以编辑、测试并发布可复用版本 |
| A4 | 算子材料与维护者发行关联 | 继续人工受控发行；不承诺零代码插件接入 | 接入材料、审核和部署事实可追踪 |
| A5 | 条件、scatter、子流程与源码编辑 | 分支/实例测试覆盖；显式版本变更差异；只读保护未知特性 | 支持已验证的高级受限 CWL 编辑 |

建议 A1 内最先进行小范围技术验证：以 Filter/Aggregate/Profile 三类参数验证描述生成、字段表示和只读 DTO 往返。它不是业务运行验收，不用短接节点代替后续 A3 的真实容器测试。

首次完整可用版本仍是 A3。不要把“已显示 11 个算子”当成“已经交付工作流编辑器”。
